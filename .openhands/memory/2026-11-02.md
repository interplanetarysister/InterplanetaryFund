### Technique: PostgREST as a schema oracle with only the anon key
- `?select=<col>&limit=1` -> HTTP 400 "column ... does not exist" means ABSENT;
  200/401/403 means the column EXISTS (RLS may deny the row read, which is fine).
- `?select=id&limit=1` -> 404 means the TABLE does not exist.
- OpenAPI `/rest/v1/` root needs a SECRET key, so it is NOT usable.
- `select=*` is blocked by column-level grants (42501); name columns explicitly.
- Row counts: header `Prefer: count=exact` + `Range: 0-0` -> Content-Range "0-0/N".
- IMPORTANT false-positive trap: a POST naming a nonexistent column returns 400
  from PostgREST's parser BEFORE RLS runs, so it looks like "write allowed" but
  proves nothing. Use real columns so the request reaches RLS (then 401).

### SYSTEMATIC PRODUCTION PATTERN: identity columns withheld from anon
Production withholds the account-uuid columns from anon:

NOTE: 401 can mean EITHER "column absent" (if the whole select is rejected) OR
"column present but not granted". Distinguish: a single-column select that 401s while

Both are SECURITY DEFINER, search_path pinned, STABLE, revoke from public then grant
to anon/authenticated.

### Generation decisions that matter (do not "simplify" these)
- string->text, number->numeric, boolean->boolean, integer->integer, object/array->jsonb.
  jsonb for object/array because the reference stores free-form structured values and
  narrowing rejects data the app already accepts. Union ["string","null"] -> non-null
  member, stays nullable.
- enum -> check constraint ONLY if every member is a usable string literal (97 of 150
  qualify). Others left permissive rather than given a WRONG constraint.
- default emitted only for boolean/number. String defaults OMITTED on purpose (they encode
  business choices; a wrong default is harder to spot than a missing one).
- IMPLICIT columns added to every table: created_date, updated_date, created_by_id.
  75/184 functions use created_by_id, 53 use created_date. Also created_at/updated_at
  emitted (16 and 12 entities DECLARE them as properties -> would collide with implicit
  pair and fail the migration).
- id is TEXT (original Base44 record ids, matching the blog tables).
- DENY-BY-DEFAULT: RLS on, ZERO grants to anon/authenticated, no policies. Purely additive
  (only create table / enable rls / revoke all against its own tables).

### SQL gotchas learned here
- Postgres rewrites `col in (...)` as `col = ANY (ARRAY[...])` in pg_get_constraintdef, and
  wraps in extra parens: `CHECK (((type IS NULL) OR ...))`. Parse the column from the
  `IS NULL` prefix, not from the membership test. Regex: /check\s*\(+\s*"?([a-z0-9_]+)"?\s+is\s+null/i
- `create table if not exists` + a table that already exists = SILENT no-op. This is why
  the legal_acceptances PK bug existed. Always check the existing table's real columns.
- Do not filter extensions inside a test walk() helper — it silently made an assertion
  vacuous (my .sql filter excluded the migrations I was comparing against).
- Entity-name -> table-name collisions: Community->ifund_community vs CommunityMember->
  ifund_community_member (distinct, fine). Generator throws on collision.
