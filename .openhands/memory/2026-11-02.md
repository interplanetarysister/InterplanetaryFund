## B20 — live content-injection hole (fixed pending apply)

Committed blog migration's insert policy was self-referential:
`with check (owner_auth_user_id = auth.uid())` — never compares blog_id to the
blog's owner. Any authenticated account could insert a PUBLISHED entry under the
official Reporter blog, and `anon` could read it. Reproduced on PGlite with a
non-owner; the repo suite now keeps that as a named regression guard.
Live because the deployed ROOT app holds the write path (`src/pages/MyBlog.jsx`
via `src/lib/blogs.js`). Fix: `pending/20261102_ifund_blog_entry_ownership_fix.sql`
(EXISTS against ifund_blogs, insert/update USING+WITH CHECK/delete). Independent
of the member-schema migration. 8 tests in `tests/blog-entry-ownership.test.js`.

## B16 was only half fixed (95f30cb)

My first B16 fix gated INSERT only. A suspended owner could still publish by
UPDATING a draft created while active, and still edit content. Reproduced on
PGlite: `update ifund_campaigns set status='active'` changed 1 row while
suspended. Fixed by adding an UPDATE policy on ifund_campaigns with the lifecycle
check in BOTH `using` and `with check`. DELETE stays owner-only on purpose (a
suspended account may clean up its own drafts). ifund_posts needs nothing — the
committed set gives it no UPDATE policy. 10 tests in
`tests/account-lifecycle-write-gate.test.js`.
=> LESSON: when a lifecycle/authorization gate is added, cover EVERY mutating
   verb (insert/update/delete), not just the obvious one. The bypass is almost
   always update.
