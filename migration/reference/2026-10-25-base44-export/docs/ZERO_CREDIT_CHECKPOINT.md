## External-sync CAS repair handoff — 2026-10-13

- **Capability inspected:** distributed serialization for explicit, request-triggered external fundraising sync in the existing Base44 architecture.
- **Open-source candidates evaluated:** [DirtyHairy/async-mutex](https://github.com/DirtyHairy/async-mutex) (MIT; maintained and compatible with JavaScript, but process-local only, so it cannot serialize Base44 serverless instances and provides no cross-instance security boundary); [mike-marcacci/node-redlock](https://github.com/mike-marcacci/node-redlock) and [sesamecare/redlock](https://github.com/sesamecare/redlock) (MIT; maintained distributed-lock implementations, but require Redis/ioredis plus new infrastructure and possible cost, while adding an external credential, attack, dependency/supply-chain, availability, and operations surface).
- **Decision and security boundary:** reject those dependencies for this repair and reuse repository-native Base44 conditional `updateMany` compare-and-set. This avoids a new supply-chain/runtime dependency and preserves the current zero-cost/Base44 boundary, but it is safe only with exact observed-state predicates, `updated === 1`, read-after-write verification, and fail-closed handling.
- **Implementation boundary:** request traffic never creates the singleton mutex because `claim_key` is not database-unique. Exactly one release-provisioned `mutex:external-sync:v1` row is required; zero or multiple rows fail closed without persistent writes. Acquisition compares the observed token and expiry so a stale waiter cannot steal a same-token renewed lease. Lease ownership is conditionally renewed and re-read immediately before rate-claim, request-claim, and run writes. Completion conditionally updates only the matching in-progress run/claim and verifies the stored result.
- **Controlled Base44 release provisioning (one-time):** completed on 2026-10-13 using the authorized Base44 data tool. The safe procedure is: first query `ExternalSyncClaim` with the exact filter `{"claim_key":"mutex:external-sync:v1"}` and retrieve enough rows to detect ambiguity. If the result count is not exactly zero, do not create or retry; one row means verify it, and more than one means keep sync fail-closed and escalate. When and only when the count is zero, create one row with `claim_key="mutex:external-sync:v1"`, `claim_type="mutex"`, `request_key="mutex"`, `request_id="mutex"`, `request_fingerprint="mutex-v1"`, `job_type="external_funds"`, `actor_user_id="system"`, `attempt_number=0`, `claimed_at="1970-01-01T00:00:00.000Z"`, `lock_token=""`, and `lock_expires_at="1970-01-01T00:00:00.000Z"`. If the create response is ambiguous, re-read and never blindly retry.
- **Provisioning proof:** completed 2026-10-13. The authorized pre-create exact-key query returned count `0`; one row was created; the immediate read-after-write exact-key query returned count `1`. Authoritative Base44 row id: `6ace0b759e9a19a17463522b`. The stored row has `claim_type="mutex"`, empty `lock_token`, epoch `lock_expires_at="1970-01-01T00:00:00.000Z"`, and the expected immutable identity fields. Never create another coordinator row; a future count of zero or more than one is a failed release and must leave Sync now unavailable.
- **Test plan:** behavioral contention tests cover concurrent first use without a coordinator, a stale waiter racing a same-token lease renewal, six-request rate contention, lease ownership loss immediately before writes, and stale completion racing a recovered retry; then run typecheck, lint, payment/financial regression tests, and production build.
- **Campaign-import recovery extension:** one server-derived `target_key` binds all explicit request UUIDs for the same owner/connection to one durable `SyncRun`, while the admin-only `ExternalCampaignImportOperation` holds raw connection identity, an unguessable server-generated recovery capability, snapshot, active claim, and converged record IDs. A Campaign carries only `external_import_private_marker`, protected by Base44 field-level security: only admin/service-role access may create, read, update, or delete it. The import function creates the draft through service-role access while setting the authenticated `created_by_id` explicitly; ordinary campaign creation remains owner-scoped and cannot supply the marker. Campaign function responses use a shared explicit allowlist, so service-role records—including `saveCampaign` updates—cannot serialize current, legacy, or future server-only fields. The owner-readable import record no longer receives the recovery secret and recovers by its immutable admin-created operation key. Every provider discovery and durable import side effect is preceded by conditional `active_claim_key` fencing; stale attempts fail closed after TTL takeover. Failed target runs remain recoverable by a later explicit request; successful targets replay without provider work. This remains request-triggered and does not authorize background sync.
- **Recovery OSS review:** [Temporal TypeScript SDK](https://github.com/temporalio/sdk-typescript) is MIT, actively maintained, and supports Node 20/22/24, but durable workers require a Temporal service plus Node-native worker/runtime components, adding credentials, network/availability, supply-chain, operations, and cost outside Base44. [@node-idempotency](https://github.com/mahendraHegde/node-idempotency) is MIT and maintained with memory/Redis/Postgres adapters, but its framework middleware is request-key scoped and distributed safety requires another datastore/adapter; it does not by itself close the campaign-create/persistence crash window. [saga-engine](https://github.com/Grafikui/saga_engine) is MIT and crash-oriented but comparatively immature, requires PostgreSQL/advisory locks, and explicitly leaves re-execution possible when a side effect succeeds before step persistence. All were rejected for this repair.
- **Recovery decision/security/cost:** reuse Base44 `SyncRun`, the global conditional mutex, conditional entity updates, one narrowly scoped private operation entity, and native Base44 field-level security. The maintained [base44/skills](https://github.com/base44/skills) reference is MIT-licensed and documents independent create/read/update/delete rules per field; no new package, service, credential, or operating cost is introduced. Authority never comes from owner-writable Campaign data: the private operation binds the capability to owner, connection, fingerprint, active claim, snapshot, and converged IDs, while the Campaign correlation marker is unreadable and unwritable—including at create time—to owners. Existing legacy recovery fields remain admin-only for every operation but grant no authority. Tests cover ordinary owner campaign creation, the post-import-create crash, save-response serialization, attempted owner marker creation and movement to an arbitrary campaign, mutable owner-visible fields, response-secret absence, two UUIDs for one connection, and a paused stale attempt resuming after claim takeover.
- **Active-worker fencing extension:** every request-only external-fund/discovery/refresh handler now fences its exact `active_claim_key` immediately before provider I/O and again before each durable canonical, observation, campaign, import, or connection write. The fence atomically heartbeats `started_at`; stale retry takeover uses compare-and-set against the previously observed claim, status, start time, and heartbeat, so a live heartbeat defeats an obsolete takeover read. A worker that detects replacement performs no provider/write callback and emits no stale failure audit. Failure audits in fund sync, discovery, imported-campaign refresh, and import are eligible only when current-claim failure finalization succeeds; a provider error that resumes after takeover cannot write failure state or an audit. Behavioral tests replace the claim and prove the old worker makes zero provider calls and zero durable writes, then exercise all four handlers' stale-versus-current provider-failure audit gates. **OSS reuse check:** the maintained MIT-licensed [DirtyHairy/async-mutex](https://github.com/DirtyHairy/async-mutex) remains process-local and cannot strengthen a distributed Base44 CAS boundary; Redis-based Redlock implementations add a datastore, credentials, network failure modes, and operating/security cost. This repair therefore reuses the existing Base44 conditional-finalization contract and proven sibling-handler pattern, adding no dependency, service, secret, hosting change, or cost.
- **Node 20 verification OSS review:** [privatenumber/tsx](https://github.com/privatenumber/tsx) and [evanw/esbuild](https://github.com/evanw/esbuild) are active MIT projects with Node 20/TypeScript support, but adding either solely for two JavaScript-compatible `.ts` contract modules would expand the dependency/supply-chain and install surface. The repair instead reuses Node's built-in ESM loader hook with a small repository loader limited to `.ts` files whose imported test closure is standards-compliant JavaScript; the shared campaign response allowlist now uses JSDoc rather than runtime-invalid TypeScript assertions or annotations. It introduces no broad regex transpiler, package, credential, service, hosting change, or cost; actual TypeScript remains covered by the existing compiler. The complete external-fund command, including request-sync and campaign-import convergence behavioral suites, passes Node 20.20.2 and the Base44 Node 24.21 runtime.
- **Rollback plan:** revert the handler fences, heartbeat/takeover CAS, Node loader command, and behavioral/static tests together. Do not re-enable request-path mutex creation or remove finalization CAS. If the release-provisioned coordinator is absent, leave sync unavailable rather than weakening serialization.
